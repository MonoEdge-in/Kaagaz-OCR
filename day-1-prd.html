1Project context

What we're building

A document service that reads the company's English business documents (PDFs, Excel and CSV files, scans, photos and handwritten pages), turns them into clean rows in PostgreSQL plus searchable text, and manages the files. A colleague's NL-to-SQL agent, built with Hermes, then answers plain-English questions such as “How much did we pay Shinde Traders last quarter?” from those tables.

Reading the text isn't enough. NL-to-SQL needs typed tables such as invoices.total and invoice_lines.quantity, and every value must trace back to its page and position so answers can be checked.

How a document moves through the system

Every upload runs the same seven steps in a Temporal workflow. Today only Upload is real; the rest are placeholders that later days replace.

  1. UploadThe browser sends the file to storage and a workflow starts.Real today
  2. RegisterFingerprint the file, skip duplicates, file the original.Day 2
  3. RouteDecide per page: spreadsheet, text-layer PDF or scan.Day 2
  4. ParseTurn pages into blocks with positions, using PaddleOCR for scans.Days 2–3
  5. ExtractQwen3.5 fills a schema for each document type.Day 4
  6. ValidateRules check the values; failures wait for a person.Day 4
  7. IndexChunk and embed the text for search.Day 5

Ground rules

  • English documents only.
  • Everything runs on one laptop, with no GPU.
  • Sample documents only. No real client files on the laptop.
  • Every setting comes from environment variables in .env: no hard-coded hosts, keys or paths. Moving to AWS must be a settings change, not a code change.
  • Uploads add rows, never tables or databases.
  • Only IDs and small values pass through Temporal, never file contents.

2Day 1 goal

By the end of Day 1, a person signs in to the basic UI, uploads a file, and watches it move from Uploading to Published while a Temporal run completes its placeholder steps.

The upload flow built today

  1. The UI asks the API for an upload, sending the file name, type and size.
  2. The API validates them and inserts an uploads row with status pending.
  3. The API returns the upload ID and a signed PUT link that expires in 15 minutes.
  4. The browser sends the file straight to SeaweedFS under incoming/{upload_id}/.
  5. The UI tells the API the upload finished.
  6. The API checks the object exists with the stated size.
  7. The API starts ProcessDocument with workflow ID upload-{upload_id}.
  8. Temporal hands the worker one task per step.
  9. The worker creates the documents row and updates its status and current step.
  10. The worker reports each step done. Temporal records it, so a restarted worker resumes from there.
  11. The UI polls every 3 seconds while anything is in progress.
  12. The API reads each upload's status from PostgreSQL.

Definition of done

  • docker compose up starts PostgreSQL, SeaweedFS, Temporal, the API and the worker with no errors.
  • Alembic creates every table in section 4 plus the pgvector extension, and alembic downgrade base removes them cleanly.
  • GET /health reports the database, storage and Temporal as reachable.
  • Uploading a PDF, an Excel file and a photo at once through the UI puts all three in SeaweedFS under incoming/.
  • Each upload starts one Temporal run, visible at localhost:8233, and every placeholder step completes.
  • The UI shows each file reaching Published without a page reload.
  • Stopping the worker mid-run and starting it again lets the run finish from where it stopped.
  • The README explains how to run everything; .env.example is committed, and no secrets are.

4Database schema with Alembic

SQLAlchemy 2 models live in shared/ and Alembic migrations in migrations/, connecting through DATABASE_URL. The first migration, 0001_initial, enables the vector extension and creates every table below, including ones Day 1 doesn't write to yet, so later days add code rather than reshaping the schema.

Conventions

  • UUID primary keys (gen_random_uuid()), and created_at and updated_at as timestamptz on every table.
  • snake_case names, with an index on every foreign key.
  • Status and type fields are text with a CHECK constraint, which is easier to extend than PostgreSQL enums.
  • Soft delete through deleted_at on documents and folders.
  • A position on a page is a bbox of [x0, y0, x1, y1] in pixels of the page image, always stored with its page.
  • Money is numeric(14,2); quantities are numeric(14,3).

Steps

  1. Initialise Alembic with its async template; env.py reads DATABASE_URL.
  2. Write 0001_initial, by hand or from autogenerate, then review it line by line. The vector extension and the HNSW index need adding by hand.
  3. Run alembic upgrade head from the migrate service on every docker compose up.
  4. Run alembic downgrade base, then upgrade again, to prove the migration reverses cleanly.

Done when

  • Every table above exists, and the vector extension is installed.
  • Downgrading to base and upgrading again runs without errors.

5FastAPI app

The API is the front door: the UI talks only to it, and it's the only part that hands out access to storage. FastAPI's interactive docs at /docs double as the contract for the UI.

Structure

  • An app factory in api/main.py with routers for health, auth, uploads and documents.
  • Settings loaded from .env with pydantic-settings.
  • Async SQLAlchemy sessions over asyncpg, using the models in shared/.
  • A Temporal client created once at startup.
  • The basic UI's static files mounted at /.

Storage helper

In shared/storage.py, used by the API today and by the worker from Day 2.

  • Creates the bucket on startup if it's missing.
  • Key layout: incoming/{upload_id}/{filename} today; originals/{sha256}.{ext}, pages/{doc_id}/{n}.png and parsed/{doc_id}/v{run}.json from Day 2.
  • Functions for a signed upload link (PUT, 15 minutes, content type fixed), a signed download link, object info (exists and size), copy, and put and get of bytes.
  • Uses boto3 with path-style addressing and signature version 4, which S3-compatible stores like SeaweedFS need.
  • Signed links use S3_PUBLIC_ENDPOINT_URL so the browser can reach them; server-side calls use S3_ENDPOINT_URL.

Dev sign-in

  • POST /auth/dev-login takes a display name and returns a signed token in an HttpOnly cookie (SameSite=Lax, valid 12 hours).
  • Every endpoint except /health and /auth/dev-login requires it. The name is written to uploaded_by and audit_log.actor.
  • Keep all of it behind one current_user dependency, so Cognito can replace it later without touching the routes.

Endpoints

MethodPathWhat it does

Rules

  • Accepted files: PDF, XLSX, XLS, CSV, PNG, JPG and TIFF. Check both the extension and the declared content type.
  • Errors share one JSON shape, {"error": {"code": "…", "message": "…"}}: 400 for bad input, 401 without sign-in, 404 for unknown IDs and 409 for conflicts.
  • Every state change writes an audit_log row.
  • Logs are structured JSON, with a request ID on every line.

Done when

  • /docs lists every endpoint above, and /health is green.
  • An upload made with curl, or through the UI, starts a Temporal run.

6Temporal workflow

Temporal runs each document's steps in order, retries failed steps, and remembers progress, so a crashed worker picks up where it stopped. The dev server runs with a database file so its state survives restarts, and its web UI at localhost:8233 shows every run. Use the default namespace.

ProcessDocument(upload_id)

Runs these activities in order. Today each placeholder logs, waits PLACEHOLDER_STEP_SECONDS, and records its name in documents.current_step.

ActivityDay 1 behaviourBecomes real on
register_uploadCreates the documents row (status processing), links it to the upload, and marks the upload registered.Day 2: fingerprint, duplicates, originals/
route_pagesPlaceholderDay 2
parse_pagesPlaceholderDays 2–3
extract_fieldsPlaceholderDay 4
validate_fieldsPlaceholderDay 4
index_documentPlaceholderDay 5
publish_documentSets the status to published.Real today
  • Define the review_finished signal now, even though it does nothing yet, so the API's contract is fixed.
  • If a step fails for good, a final step sets the status to failed and records the error.

Settings for every activity

  • A start-to-close timeout: 5 minutes for the placeholders.
  • Retries start after 2 seconds, double each time, and stop after 5 attempts. Bad input is marked non-retryable.
  • The workflow ID is upload-{upload_id}, so one upload can never start two runs.
  • Workflow code does no I/O. Database, storage and model calls happen only inside activities.
  • Activities take and return IDs and small values only, never file contents.

Worker

A separate container that registers the workflow and activities on the cpu task queue and shuts down cleanly when stopped. The gpu queue name is already in settings; its worker arrives on Day 3.

Done when

  • A completed upload starts a run, and the Temporal UI shows all seven activities completed.
  • Stopping the worker mid-run and starting it again lets the run finish without starting over.

7Basic UI

Lets anyone try the pipeline without curl. Plain HTML, CSS and a small JavaScript file served by FastAPI at /: no framework, no build step, no Node.

Screens

  • Sign-in. A name field and a Continue button, with a note that this dev login is replaced by Cognito later.
  • Documents home. A header with the app name, the signed-in user and Sign out. An upload area that takes drag-and-drop or a file picker, accepts several files at once, and shows a progress bar for each. Below it, a Recent uploads table: file name, type, size, uploaded by, uploaded at, status, and actions to view the run in the Temporal UI or download the file once it's registered.
  • Upload detail. Opens from a row: the file's details, current step, timestamps and workflow ID.

Statuses

Shown as chips: Uploading (still in the browser), Waiting (pending or uploaded), Processing with the step name, Needs review (from Day 4), Published, Duplicate (from Day 2) and Failed with the reason. The API computes display_status, so the UI never works it out itself.

Behaviour

  • Check the file type and size in the browser before uploading; the server checks again.
  • While any row is Uploading, Waiting or Processing, refresh the table every 3 seconds. Stop once everything has settled.
  • Empty state: “No documents yet. Drop a PDF, spreadsheet or image to start.”
  • Errors appear next to the file they belong to and say what to do next.
  • Works with a keyboard: the upload area has a real button, and focus is always visible.

Done when

  • A signed-in user uploads a PDF, an Excel file and a photo at once, and watches each reach Published without reloading the page.
  • Each row's View run link opens that run in the Temporal UI.

9Risks and fallbacks

If this happensDo this
The browser can't upload straight to SeaweedFS because of CORS errorsAllow http://localhost:8000 in SeaweedFS. If that isn't working within 30 minutes, send uploads through a laptop-only API endpoint behind the same client function, and note it for later.
Signed links fail with a signature errorCheck path-style addressing and signature version 4, and that the host in the link matches S3_PUBLIC_ENDPOINT_URL.
Docker is slow on WindowsKeep the repo in the WSL file system, and give WSL enough memory in .wslconfig.
A task runs well past its estimateFlag it early and move on. Placeholders are fine today.

10End-of-day hand-off

  • A pull request, or a pushed branch, with the work above.

  • Notes on anything that took longer than expected, and any setting that differs from this document.
